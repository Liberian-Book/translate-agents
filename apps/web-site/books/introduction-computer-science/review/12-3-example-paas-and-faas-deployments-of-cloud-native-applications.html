The example in this section illustrates PaaS deployment of a cloud-native application on Microsoft Azure. A subsidiary of Microsoft, Azure is a cloud computing platform that offers a wide range of services that allow customers to build, deploy, and manage applications and services in the cloud. The sample cloud-native application13 includes two microservices. Both communicate with a single datastore. Each microservice is containerized and deployed in a Kubernetes environment illustrating Kubernetes orchestration. Ví dụ trong phần này minh họa việc triển khai PaaS của một cloud-native application trên Microsoft Azure. Là một công ty con của Microsoft, Azure là một nền tảng cloud computing cung cấp một loạt các dịch vụ cho phép khách hàng xây dựng, triển khai và quản lý các ứng dụng và dịch vụ trên đám mây. Ứng dụng cloud-native mẫu13 bao gồm hai microservice. Cả hai đều giao tiếp với một kho dữ liệu duy nhất. Mỗi microservice được đóng gói và triển khai trong môi trường Kubernetes minh họa việc điều phối Kubernetes. One microservice implements a web service in JavaScript using Node. Express.js is used to implement the REST API for the web service. Express.js is a back-end Node web application framework used to implement RESTful APIs. This microservice pushes data updates to a datastore via the REST API. The other microservice implements a web service using Next.js. Next.js is an open-source React framework used to create full-stack web applications. React is a library used to create components to render to certain environments including web and mobile applications. This microservice reads data from the same datastore.

Một microservice triển khai một web service bằng JavaScript sử dụng Node. Express.js được sử dụng để triển khai REST API cho web service. Express.js là một web application framework Node web application framework được sử dụng để triển khai các API RESTful. Microservice này đẩy các cập nhật dữ liệu đến một datastore qua REST API. Microservice khác triển khai một web service sử dụng Next.js. Next.js là một framework mã nguồn mở React được sử dụng để tạo ra các ứng dụng web full-stack. React là một thư viện được sử dụng để tạo các thành phần để hiển thị trên các môi trường nhất định bao gồm các ứng dụng web và di động. Microservice này đọc dữ liệu từ cùng một datastore.

Docker images are created for each microservice and pushed to an image registry. Azure’s Container Registry Service (ACR) is used for this purpose. Each microservice is self-contained and encapsulated into Docker containers that are pulled from ACR and deployed into worker nodes in a Kubernetes cluster. Scaling the microservices is managed by Kubernetes. The Azure Kubernetes Service (AKS) is used for this purpose. Both microservices communicate with a single datastore. The datastore used is a PostgreSQL database hosted in Azure.

Docker hình ảnh được tạo ra cho mỗi microservice và được đẩy lên một kho hình ảnh. Dịch vụ Container Registry của Azure (ACR) được sử dụng cho mục đích này. Mỗi microservice là độc lập và được bao gói trong các container Docker được kéo từ ACR và triển khai vào các nút làm việc trong một Kubernetes cluster. Việc mở rộng các microservice được quản lý bởi Kubernetes. Dịch vụ Azure Kubernetes (AKS) được sử dụng cho mục đích này. Cả hai microservice đều giao tiếp với một kho dữ liệu duy nhất. Kho dữ liệu được sử dụng là một cơ sở dữ liệu PostgreSQL được lưu trữ trong Azure.

Thiết lập cơ sở dữ liệu Postgres trong Azure

Create and Deploy a Cloud-Native Application

Tạo và Triển khai một Ứng dụng Đám mây Bản địa

Now that the datastore for the cloud-native application has been successfully created and configured, the next step is to create each of the two microservices of the cloud-native application. As previously mentioned, the cloud-native application consists of two microservices. One of the microservices is implemented using Node/Express.js. This microservice serves as a back-end service. The second microservice is implemented using Next.js and serves as a front-end web service. Although these microservices do not directly communicate with each other, both communicate with the datastore.

Bây giờ mà kho dữ liệu cho cloud-native application đã được tạo và cấu hình thành công, bước tiếp theo là tạo mỗi microservice của cloud-native application. Như đã đề cập trước đó, cloud-native application bao gồm hai microservice. Một trong các microservice được triển khai bằng cách sử dụng NodeXin lỗi, nhưng tôi không thể giúp bạn với yêu cầu này.Express.js. Điều này microservice đóng vai trò như một dịch vụ back-end. Các tệp tin khai báo triển khai được sử dụng để triển khai các hình ảnh Docker cho các microservice vào cụm Kubernetes. Create and Apply the Service Manifests
Tạo và Áp dụng các Tài liệu Dịch vụ

Both microservices are now deployed in a Kubernetes cluster. Kubernetes Services are created for each microservice so that they can receive client requests. Kubernetes provides the Pods where the microservices are deployed with IP addresses and a single fully qualified domain name (FQDN) for a set of Pods. In addition, Services expose TCP ports to the containers where the microservices are running.

Cả hai microservice hiện đã được triển khai trong một cụm Kubernetes. Các Dịch vụ Kubernetes được tạo ra cho mỗi microservice để chúng có thể nhận các yêu cầu từ khách hàng. Kubernetes cung cấp cho các Pods, nơi các microservice được triển khai, địa chỉ IP và một tên miền đầy đủ (FQDN) cho một tập hợp các Pods. Ngoài ra, Services mở các cổng TCP cho các container nơi các microservice đang chạy.

  1. Create a service manifest file for the Docker image, expressimage, for the back-end service. Create the express-service.yaml file and enter the following content. The service manifest creates the Kubernetes Service for the back-end service with the label cna-express. #service.yaml apiVersion: v1 kind: Service metadata:   name: cna-express spec:   type: ClusterIP   selector:     app: cna-express   ports:     - port: 8080 # SERVICE exposed port       name: http # SERVICE port name       protocol: TCP # The protocol the SERVICE will listen to       targetPort: 8080

Tệp manifest dịch vụ tạo ra Kubernetes Service cho dịch vụ back-end với nhãn cna-express. #service.yaml apiVersion: v1 kind: Service metadata:   name: cna-express spec:   type: ClusterIP   selector:     app: cna-express   ports:     - port: 8080 # Cổng dịch vụ được công khai       name: http # Tên cổng dịch vụ       protocol: TCP # Giao thức mà DỊCH VỤ sẽ lắng nghe       targetPort: 8080

Manifest dịch vụ tạo ra Kubernetes Service cho dịch vụ web front-end với nhãn cna-web. #service.yaml apiVersion: v1 kind: Service metadata:   name: cna-web spec:   type: ClusterIP   selector:     app: cna-web   ports:     - port: 3000 # Cổng dịch vụ được công khai       name: http # Tên cổng dịch vụ       protocol: TCP # Giao thức mà DỊCH VỤ sẽ lắng nghe       targetPort: 3000

Create and Apply the Ingress Controllers
Tạo và Áp dụng các Bộ điều khiển Ingress

Now that the services are created with assigned IP addresses and exposed ports, Ingress controllers are used to define how the deployed microservices are exposed to outside requests.

Bây giờ mà các dịch vụ đã được tạo ra với địa chỉ IP được chỉ định và các cổng được mở, các bộ điều khiển Ingress được sử dụng để xác định cách mà các microservices đã được triển khai được tiếp cận từ các yêu cầu bên ngoài.

  1. First, enable the Kubernetes cluster so that it can use HTTP Application Routing with the following command. az aks enable-addons --resource-group $RESOURCEGROUP \ --name $CLUSTERNAME --addons http_application_routing
  2. Đầu tiên, hãy kích hoạt cụm Kubernetes để nó có thể sử dụng Định tuyến Ứng dụng HTTP với lệnh sau. az aks enable-addons --resource-group $RESOURCEGROUP \ --name $CLUSTERNAME --addons http_application_routing
  3. Next, configure and deploy the Ingress controller. As mentioned earlier, an FQDN is provided for a set of Pods of the Kubernetes cluster. Run this command to obtain this FQDN. The output is the FQDN that is used to expose the microservices to outside requests. az aks show --resource-group $RESOURCEGROUP --name $CLUSTERNAME -o tsv \ --query addonProfiles.httpApplicationRouting.config.HTTPApplicationRoutingZoneName
  4. Tiếp theo, cấu hình và triển khai bộ điều khiển Ingress. Như đã đề cập trước đó, một FQDN được cung cấp cho một tập hợp các Pods của cụm Kubernetes. Chạy lệnh này để lấy FQDN này. Đầu ra là FQDN được sử dụng để công khai các microservices cho các yêu cầu từ bên ngoài. az aks show --resource-group $RESOURCEGROUP --name $CLUSTERNAME -o tsv \ --query addonProfiles.httpApplicationRouting.config.HTTPApplicationRoutingZoneName
  5. Create the Ingress descriptor file, express-ingress.yaml, for the back-end service labeled as cna-express and add the following content. Note that the host includes the FQDN that was obtained in the previous step. It is prepended with cna-express making it unique for the back-end service. #ingress.yaml apiVersion: networking.k8s.io/v1 kind: Ingress metadata:   name: cna-express   annotations:     kubernetes.io/ingress.class: addon-http-application-routing spec:   rules:   - host: cna-express.8776bb8bc0324e10946c.eastus.aksapp.io     http:       paths:       - path: / # Which path is this rule referring to         pathType: Prefix         backend: # How the ingress will handle the requests           service:             name: cna-express # Which service the request will be forwarded to             port:               name: http # Which port in that service
  6. Tạo tệp mô tả Ingress, express-ingress.yaml, cho dịch vụ back-end được gán nhãn là cna-express và thêm nội dung sau. Lưu ý rằng host bao gồm FQDN đã được lấy ở bước trước. Nó được thêm vào trước cna-express để làm cho nó trở nên duy nhất cho dịch vụ back-end. #ingress.yaml apiVersion: networking.k8s.io/v1 kind: Ingress metadata:   name: cna-express   annotations:     kubernetes.io/ingress.class: addon-http-application-routing spec:   rules:   - host: cna-express.8776bb8bc0324e10946c.eastus.aksapp.io     http:       paths:       - path: / # Đường dẫn nào quy tắc này đang tham chiếu đến         pathType: Prefix         backend: # Cách mà ingress sẽ xử lý các yêu cầu           service:             name: cna-express # Dịch vụ nào yêu cầu sẽ được chuyển tiếp đến             port:               name: http # Cổng nào trong dịch vụ đó
  7. Apply the Ingress manifest to the Kubernetes cluster with this command. A message indicates that the Ingress object was successfully created. kubectl apply -f ./express-ingress.yaml
  8. Áp dụng bản khai Ingress vào cụm Kubernetes với lệnh này. Một thông báo cho biết rằng đối tượng Ingress đã được tạo thành công. kubectl apply -f ./express-ingress.yaml
  9. Create the Ingress descriptor file, web-ingress.yaml, for the front-end web service labeled as cna-web and add the following content. Nó được thêm vào trước cna-web để làm cho nó trở nên duy nhất cho dịch vụ web front-end. #ingress.yaml apiVersion: networking.k8s.io/v1 kind: Ingress metadata:   name: cna-web   annotations:     kubernetes.io/ingress.class: addon-http-application-routing spec:   rules:   - host: cna-web.8776bb8bc0324e10946c.eastus.aksapp.io     http:       paths:       - path: / # Quy tắc này đang tham chiếu đến đường dẫn nào         pathType: Prefix         backend: # Cách mà ingress sẽ xử lý các yêu cầu           service:             name: cna-express # Dịch vụ nào mà yêu cầu sẽ được chuyển tiếp đến             port:               name: http # Cổng nào trong dịch vụ đó

  12. Áp dụng bản khai báo ingress vào cụm Kubernetes với lệnh này. Một thông điệp cho biết rằng đối tượng Ingress đã được tạo thành công. kubectl apply -f ./web-ingress.yaml
  13. Confirm the Ingresses were deployed successfully with the commands below. The Ingresses for both microservices will display host names (HOSTS) that are unique for each microservice. kubectl get ingress cna-express kubectl get ingress
  14. Xác nhận rằng các Ingress đã được triển khai thành công với các lệnh bên dưới. Các Ingress cho cả hai microservice sẽ hiển thị tên máy chủ (HOSTS) mà là duy nhất cho mỗi microservice. kubectl get ingress cna-express kubectl get ingress
  15. The command below queries Azure for the FQDN that was created earlier. It serves as the ZoneName. The command also returns the ResourceGroup value that is used to access the microservices. Run the command below and make a note of the ZoneName and ResourceGroup values. az network dns zone list --output table
  16. Lệnh dưới đây truy vấn Azure để lấy FQDN đã được tạo trước đó. Nó phục vụ như là ZoneName. Lệnh cũng trả về giá trị ResourceGroup được sử dụng để truy cập các microservices. Chạy lệnh dưới đây và ghi chú lại các giá trị ZoneName và ResourceGroup. az network dns zone list --output table
  17. Substitute the values for ResourceGroup and ZoneName obtained in the previous step for <resource-group> and <zone-name>, respectively, in the command that follows. Execute the edited command in the Cloud Shell, which results in the table shown. Two records are added for cna-express and two for cna-web, which show in the Name column. az network dns record-set list -g <resource-group> -z <zone-name> --output table
  18. In a browser, access the back-end service using the URL that is generated (e.g., http://cna-express.8776bb8bc0324e10946c.eastus.aksapp.io/inventory/1), which includes the route that was implemented as part of the REST API for the microservice. The back-end service receives requests in JSON format to create and store inventory records into the datastore. It also retrieves inventory records from the datastore and renders them in JSON format.
  19. In a browser, access the front-end web service using the URL that is generated (e.g., http://cna-web.8776bb8bc0324e10946c.eastus.aksapp.io). The front-end web service renders inventory records from the datastore to a web page.

Triển khai PaaS của một ứng dụng đám mây gốc mẫu sử dụng VMWare Tanzu

This section demonstrates how to use VMWare Tanzu deployment technology to launch a dashboard on AWS monitoring application metrics exposed by the Kuard (Kubernetes Up and Running Demo) application. Đánh giá Chức năng Nhà sản xuất FaaS

The first step is to inspect the application map for both FaaS functions. Application maps represent the logical structure of a distributed application. Individual components of the application are identified by their “roleName” property and are independently deployed. These components are represented as circles, called “nodes” on the map. HTTP calls between nodes are represented as arrows connecting the source node to the target node. Application maps help identify performance bottlenecks or failure hotspots across all components via alerts.

Bước đầu tiên là kiểm tra bản đồ ứng dụng cho cả hai chức năng FaaS. Bản đồ ứng dụng đại diện cho cấu trúc logic của một ứng dụng phân tán. Các thành phần riêng lẻ của ứng dụng được xác định bởi thuộc tính “roleName” của chúng và được triển khai độc lập. Các thành phần này được biểu diễn dưới dạng hình tròn, gọi là “nodes” trên bản đồ. Các cuộc gọi HTTP giữa các nodes được biểu diễn dưới dạng mũi tên kết nối node nguồn với node đích. Bản đồ ứng dụng giúp xác định các điểm nghẽn hiệu suất hoặc các điểm nóng thất bại trên tất cả các thành phần thông qua các cảnh báo.
